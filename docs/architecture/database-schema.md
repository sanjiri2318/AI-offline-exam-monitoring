# Database Schema

This document defines the proposed database entities and relationships for the AI-Based Offline Examination Monitoring System.

## Database Responsibility

The Backend API Service is the single source of truth for persistent application data. The AI/CV Engine does not directly access the application database.

## Core Entities

### User

Stores faculty, administrator, and other authenticated system users.

### Exam

Stores examination information such as exam identity, schedule, and status.

### ExaminationRoom

Stores examination hall information.

### Seat

Stores physical seat information within an examination room.

### Student

Stores student information used by the examination monitoring system.

### StudentSeatAssignment

Associates a student with an assigned seat for a specific examination.

### Camera

Stores CCTV/IP camera information and its association with an examination room.

### CameraConfiguration

Stores camera-specific configuration such as stream and monitoring settings.

### TrackingSession

Represents a monitoring/tracking session during an examination.

### CameraTrack

Represents a tracked person within an individual camera view.

### CrossCameraTrack

Represents continuity of a tracked student across multiple camera views.

### DetectionEvent

Stores events detected or generated during monitoring.

### BehaviourEvent

Stores behaviour-related events derived from detected activity.

### RiskAssessment

Stores contextual risk assessments generated by the Backend Risk Engine.

### Incident

Stores incidents created from contextual risk analysis for invigilator attention.

### Evidence

Stores metadata for evidence associated with an incident or event. Evidence media is stored separately in the evidence-storage directory.

### SystemConfiguration

Stores configurable system-level settings.

### AuditLog

Stores important system actions for traceability.

## Main Relationships

- An Exam is associated with an ExaminationRoom.
- An ExaminationRoom contains multiple Seats.
- An ExaminationRoom can have multiple Cameras.
- A Student can have a StudentSeatAssignment for an Exam.
- A StudentSeatAssignment associates a Student with a Seat.
- A Camera can produce multiple CameraTracks during a TrackingSession.
- CameraTracks can be associated with CrossCameraTracks to maintain tracking continuity between cameras.
- DetectionEvents are associated with cameras and tracking information.
- BehaviourEvents are derived from monitoring activity and may reference related DetectionEvents.
- RiskAssessments use contextual events and are associated with the relevant monitoring context.
- Incidents are created from RiskAssessments when attention is required.
- Evidence can be associated with Events and Incidents.
- AuditLogs record important actions performed by system users or services.

## Event Data

Detection and behaviour records must remain compatible with the shared event contract defined in `docs/architecture/event-model.md`.

The shared event contract includes:

- `event_id`
- `event_type`
- `timestamp`
- `camera_id`
- `track_id`
- `student_id`
- `confidence`
- `metadata`
- `related_event_ids`

## Risk Data

RiskAssessment records must support contextual risk scoring rather than directly storing a conclusion that a student is cheating.

Risk calculations may consider multiple related events and their temporal context.

## Storage

- Application metadata and persistent records are stored in the application database.
- Evidence media is stored separately in `evidence-storage`.
- Evidence records in the database contain metadata and references to the stored media.

## Architecture Rule

The database schema is a shared contract for the Backend API Service and related project modules. Backend implementation must follow this documented structure unless the architecture is explicitly revised.
